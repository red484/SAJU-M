# 데이터 보존 현황 점검

현재 구현과 아직 확정하지 않은 거래 정보 처리 기준을 구분한다. 이 문서는 법정 보존기간에 대한 판단이나 파기 승인이 아니다.

## 읽기 전용 점검

운영 백엔드 컨테이너에서 실행한다. DB 연결 설정을 출력하거나 명령행 인수로 전달하지 않는다.

```sh
sudo docker exec saju-backend node server/retention-report.mjs
```

개발 DB는 환경에 `DATABASE_URL`을 설정하고 `npm run report:retention`으로 확인한다. 외부 DB의 경우 이 도구에는 필요한 테이블의 SELECT 권한만 있는 계정도 사용할 수 있다. 공개 API·관리자 웹 화면은 추가하지 않는다.

보고서는 DB의 같은 시점 스냅샷에서 읽기 전용 트랜잭션으로 집계한다. 각 SQL의 실행은 10초로 제한한다. 주문번호·계정·인증 토큰·질문 해시·상담 본문·답변·모델 응답을 조회 결과로 가져오지 않으며 건수와 점검 시각만 출력한다. 실행 오류는 정해진 오류 코드로 출력한다. 빈 테이블은 0으로 표시하며, 실패한 조회를 0으로 대체하지 않는다.

| 출력 | 해석 |
| --- | --- |
| orders.total / unlinked | 전체 주문 / 탈퇴 등으로 계정 연결이 없는 주문. 연결 해제는 주문 자체 삭제나 익명화 완료를 뜻하지 않는다. |
| orders.locally_usable | 계정 연결·미환불·미소진·유효기간 내 조건을 만족하는 로컬 DB 주문 수. 토스 환불 상태 재조회나 실제 구매 가능 여부의 확정이 아니다. |
| orders.expired / refunded / exhausted | 만료·환불 표시·50회 소진 주문 수. 조건이 겹칠 수 있으므로 합산해 전체 주문 수로 사용하지 않는다. |
| orders.stored_over_one_year | DB 생성 후 1년 이상 경과한 주문 수. 구매일과 DB에 복원된 시점은 다를 수 있다. 법정 보존 종료나 삭제 가능 판정이 아니다. |
| orders.inconsistent_dates | 구매일이 현재보다 1분 넘게 미래이거나 만료일이 구매일보다 이른 주문 수. 원인 확인용이다. |
| answers | 상담 답변 재시도·중복 차감 방지용 응답 행의 전체/30일 이상/1년 이상 보관 건수. 원문을 출력하지 않는다. 무료·유료 답변이 섞여 있어 결제 공급 증빙으로 간주하지 않는다. |
| operational | 만료된 인증 세션과 30일 기준을 지난 운영·통계 행 수. 시작·매시간 정리가 적용되므로 주기 사이에는 0보다 클 수 있다. 지속 증가나 정리 오류 여부를 확인한다. |

출력의 30일·1년은 진단용 연령 구간이다. 거래 기록의 법정 보존기한을 임의로 정한 것이 아니다. 출력은 합계만 담지만 운영 내부 자료로 취급하고 불필요하게 장기 보관하지 않는다.

## 현재 데이터 동작

| 저장 대상 | 현재 용도·삭제 동작 | 남은 결정 |
| --- | --- | --- |
| `saju_journals` | 프로필·상담·선택·회고·저장 답변. 보관함 삭제·탈퇴 시 삭제한다. | 거래 증빙 보관용으로 사용하지 않는다. |
| `coach_answers` | 요청 재시도 시 같은 답변을 돌려주고 중복 차감을 막는다. 응답 원문을 포함하며 계정 탈퇴 시 연쇄 삭제한다. | 응답 재시도 기간과 원문·최소 차감 정보의 분리, 유료 공급 증빙 필요 범위를 확정한다. 현재 이 행만으로 법정 거래 보존이 완성되지 않는다. |
| `toss_coach_orders` | 지급·복원·사용·환불 상태와 중복 지급 방지. 서비스 DB의 별도 테이블에 보관한다. 탈퇴 시 계정 연결을 해제하고 주문 행은 남는다. | 법정 보존 대상 필드, 보존 기산점, 분리 보관 방식·접근권한, 주문 중복 지급 방지 정보의 종료 기준, 기한 만료 파기를 확정한다. 현재 자동 파기는 없다. |
| 인증·운영·선택형 통계 | 인증은 유효기간 만료 시, 운영 로그와 통계는 30일 기준으로 정리한다. | 거래·관리자 접속 증빙에 이 정리 기준을 확대하지 않는다. [운영 로그 문서](LOG-RETENTION.md) 참조. |

## 거래 정보 파기 전 확인 순서

1. 실제 판매 채널과 상품, 거래 증빙의 법정 보존 대상·기산점, 환불·분쟁 처리 및 법적 보류 범위를 확인한다.
2. 필요한 최소 필드와 접근권한, 서비스 보관함과 분리할 저장 범위를 확정한다. 상담 원문 전체를 거래 증빙으로 무조건 보존하지 않는다.
3. 탈퇴한 주문의 재지급 방지 범위를 토스 복원 규칙과 함께 확인한다. 주문 행을 단순 삭제하면 재등록 경로가 열릴 수 있다.
4. 확정 기준으로 후보 건수·관련 데이터 영향을 먼저 검증하고, 그 뒤 실제 분리 보관·파기를 구현한다. 이 점검 도구에는 삭제 옵션이 없다.

2026년 11월 4일: 위 동작은 소스·DB 테스트로 확인했다. 운영 데이터 현황은 보고서 실행 결과로 별도 확인한다. 외부 계약·법률 검토나 토스 실결제 검증의 완료를 뜻하지 않는다.
